# AIアバターと大規模言語モデルの実運用を紐解く週

7 月中盤、日常の自動化タスクと配信用アバター構築が交錯した週でした。  
モデルの安定性を測る実験と、VRM を軸にしたモーションパイプラインの骨格合わせが同時に進行し、思考の切り替えが頻繁に起きたことが印象に残ります。

## gpt‑oss:120b と Nemotron‑120b の実運用比較

2026‑07‑11 に行った比較実験は、同一ハードウェア上で二つの 120 B パラメータモデルを交互に立ち上げ、四つの本番タスクで出力を収集したものです。  
温度設定は 0.1、構造化 JSON を要求するタスクでは max_tokens を 4096 に固定し、トークン枯渇が出力に影響しないかを防ぎました。  
URL 分類では gpt‑oss が 44 秒で 30 件すべてスキーマに適合し、空応答やエラーは一切ありませんでした。一方 Nemotron は 87 秒かかり、2 件がコンテキスト長超過で 400 エラーとなり、結果的に 28 件だけが合格しました。  
監査判定タスクでも gpt‑oss は 20 秒で有効な JSON を返し、Nemotron は 29 秒でフォーマットがずれていたため自動採点が失敗しましたが、内容自体は概ね妥当でした。  
記事要約では gpt‑oss が 8 本すべてを正常に生成し、Nemotron は 6 本だけが出力、残り 2 本は空応答となっていました。作業ログ要約では gpt‑oss が 5 件すべて正しい JSON を返したのに対し、Nemotron は全件が空もしくは JSON が壊れ、平均 480 秒という長時間を要しました。  

この結果から、長いプロンプトで構造化出力を要求すると Nemotron の推論エンジンは reasoning にトークンを消費し切り、最終的な content 部分が残らないことが分かりました。対策としては max_tokens を 8 k–16 k に増やすか、API ルーター側で reasoning_content を取得して再組み立てする方法が考えられます。実運用では、速度と空応答の有無が日次バッチ処理の信頼性に直結するため、私は gpt‑oss:120b をデフォルトとして残し、Nemotron は多条件推論が必要な限定シーンにだけ呼び出す方針に落ち着きました。

## 長文プロンプトでの構造化出力の課題と対策

上記実験を通して、トークン予算が思考に奪われる現象は短い対話では顕在化せず、実際の業務フローで初めて表面化します。私は最初、max_tokens が 4096 でも十分と考えていましたが、JSON のフィールドが 0 バイトになるケースを見て、トークン余裕が足りないことに気付きました。そこで、次回以降は「reasoning_content」も含めて取得できるよう API 呼び出しをラップし、返却されたテキストを二段階で組み立てる実装に変更しました。実装は数行のコード追加でしたが、テスト環境で同様の長文要約を走らせたときに、空応答が完全に消え、出力速度はやや低下したものの 2 倍以下に抑えられました。  

この経験は、モデル選定だけでなくプロンプト設計とトークン管理のバランスがシステム全体の安定性に直結することを再認識させました。

## AIアバター実装のロードマップとスケルトン変換

同じ週に始めたのは、コメント駆動型配信アバターの全体設計です。手元にあったのはキャラクター設定だけで、VRM ファイルは未作成でした。まずは NVIDIA の ARDY（テキストからリアルタイムに人体モーションを生成するエンジン）を選択し、Core スケルトンを VRM の Humanoid ボーンにマッピングする作業に取り掛かりました。スケルトン名と階層を一覧化し、VRM が要求する Z 前方・Y 上方向・左手系との座標変換式を自分で書き起こしたとき、軸の違いが原因で手足が逆向きになるバグに遭遇しました。オフラインで `scripts/generate.py` が出力した `.npz` データを VRM に焼き付け、ビューワで確認した結果、膝が逆に曲がっていることが判明し、変換テーブルを修正する必要が出ました。

リスクが顕在化した段階で、私は「No‑Go」判断基準を設け、スケルトン変換が 5 分以上かかるか、破綻した姿勢が 2 件以上出たら次のフェーズに進まないと決めました。実際に再試行したときは、軸合わせを一度だけ修正すればすべてのサンプルが正常に再生でき、フェーズ 3 のスパイクは合格点を得ました。

この段階で、AR​DY が提供する情報は関節位置・回転・ルート位置・足接触だけで、指先や表情は出力しないことが分かり、表情や瞬きはランタイム側で別途処理する設計にシフトしました。結果として、モーション生成は ARDY に任せつつ、表情は Audio2Face か VRM のブレンドシェイプで補完する流れが固まりました。

## AITuberKit を用いた配信環境の構築

同時に進めたのは、実際に配信に使うパイプラインの構築です。私は AITuberKit（Pixiv の ChatVRM をフォークした OSS）を選び、Claude（Anthropic）の API キーを `.env` に設定してローカルで起動しました。VRoid Studio で作成した VRM をインポートし、システムプロンプトに「明るく元気な配信者」という性格設定を書き込み、テキスト入力に対して Claude が返す応答が音声合成エンジン（VOICEVOX）で再生され、口パクが同期することを確認しました。YouTube コメント取得は YouTube Data API を用い、1 秒ごとにポーリングしてコメントが来たら即座にプロンプトに変換し、AI が返答すると同時にモーションタグが付与されて手のジェスチャーが再生されました。  

OBS ではブラウザソースとして `http://localhost:3000` を読み込み、映像合成を行いましたが、音声遅延が 300 ms 程度発生したことに気付き、Audio2Face の導入を検討するきっかけとなりました。30 分間の連続配信テストでは、CPU 使用率が 45 % 前後に留まり、メモリリークは見られませんでしたが、Claude のレートリミットに達した瞬間に応答が止まり、アイドルモードが自動で有効になることを確認しました。  

この構成は「最小工数で配信を成立させる」ことを目指したもので、AR​DY の全身モーションはまだ組み込んでいません。代わりに VMagicMirror の簡易アニメーションと Audio2Face の表情生成を組み合わせる案が次のステップとして浮上しています。

## 次にやりたいこと

今回の作業で、gpt‑oss が日次バッチの信頼性を支えること、Nemotron が特殊条件下でのみ優位になること、AR​DY のスケルトン変換が座標系の違いでつまずきやすいこと、そして AITuberKit がコメント駆動の配信を比較的手軽に実装できることがそれぞれ確認できました。残された課題は、長文構造化出力のトークン上限を安全に拡張する実装の完成と、AR​DY の出力を VRM にシームレスにリターゲットする自動マッピングスクリプトの洗練です。また、Audio2Face を組み込んだ表情生成と、全身モーションを AR​DY から取り込むフローを実証することが次の目標です。これらを段階的に統合し、速度と安定性のバランスを取りながら、最終的に「コメント → テキスト → 全身モーション → 表情・口パク → 配信」という一連のループを遅延数百ミリ秒以内で閉じることを目指しています。
